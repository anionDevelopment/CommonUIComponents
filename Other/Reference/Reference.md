| SEC-1 | open  | The script `start` in `package.json` of `NgxCountrySelector`, `NgxCultureSelector` and `NgxDarkmodeToggleButton` starts the development-server of the demo-application with `--host 0.0.0.0 --disable-host-check`. It is used by `task rd<kind><component>` and by the `webServer` of `playwright.config.ts`.                                                                                                                        | The demo-application and the sources the development-server delivers are reachable from every host of the network while the demo runs, and the protection against DNS-rebinding of the development-server is disabled. The demo-applications contain no sensitive data, so the impact is low.                                 | Found by a bug-search with focus on security (2026-10-09). Not fixed because the binding is presumably required by the visual-regression-tests which run in a container (`TFCPS_VisualRegressionTests` of ScriptCollection); a fix needs a separate start-script for the local demo which binds to `localhost` only, and has to be verified with `task uvrb<kind><component>`. |
| SEC-2 | open  | The readme of `NgxDarkmodeToggleButton` (section "Set the attribute before the first frame") tells the application to put an inline `<script>` into its `index.html`.                                                                                                                                                                                                                                                                | An application with a strict content-security-policy either has the script blocked or has to allow `'unsafe-inline'` for scripts, which weakens its protection against cross-site-scripting. Low.                                                                                                                             | Found by a bug-search with focus on security (2026-10-09). Possible fix: document that the script has to be allowed by a hash or a nonce in the content-security-policy, or provide it as a separate file.                                                                                                                                                                     |
| BUG-1 | open  | `NgxDarkmodeService` (`ngx-darkmode.service.ts`) accesses `window.localStorage` without handling exceptions. Accessing it throws a `SecurityError` if the browser blocks the storage (for example with disabled cookies or in a sandboxed iframe), and `setItem` can throw a `QuotaExceededError`. The inline script of the readme and of the demo-application has the same issue.                                                   | The callback of `afterNextRender` throws, the stored mode is never marked as read, and therefore choosing a mode with the toggle-button has no effect at all. The error is reported to the error-handler of the application.                                                                                                  | Found by a bug-search with focus on security (2026-10-09). Not fixed because it requires a decision how the component behaves without a storage (for example keeping the mode only in memory).                                                                                                                                                                                 |
| BUG-2 | open  | `MatDarkmodeToggleButton` calls `MatDarkmodeController.setMode` in `onSelectionChanged` without awaiting or handling the returned future, so an exception of `ThemeModeStore.save` is not handled. Additionally `loadPersistedMode` propagates an exception of `ThemeModeStore.load`, which in the startup-code shown in the readme (`await controller.loadPersistedMode()` before `runApp`) prevents the application from starting. | A failing store (for example `shared_preferences` on the web with a blocked `localStorage`) results in an unhandled asynchronous error when the mode is changed, and in an application which does not start at all when the stored mode is loaded.                                                                            | Found by a bug-search with focus on security (2026-10-09). Not fixed because it requires a decision how the widget behaves when the store fails.                                                                                                                                                                                                                               |
| BUG-3 | open  | `MatDarkmodeController.loadPersistedMode` applies the loaded mode unconditionally after `ThemeModeStore.load` completed, even if `setMode` was called while the load was still running.                                                                                                                                                                                                                                              | If `loadPersistedMode` is called after the application is shown (which its doc-comment allows), a mode the user chooses in the meantime is overwritten by the previously stored mode in the user-interface, while the store keeps the mode the user chose, so the user-interface and the store disagree until the next start. | Found by a bug-search with focus on security (2026-10-09). Not reachable with the startup-code shown in the readme, because there the mode is loaded before `runApp`.                                                                                                                                                                                                          |
